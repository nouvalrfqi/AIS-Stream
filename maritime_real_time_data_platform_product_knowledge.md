# Maritime Real-Time Data Platform — Product Knowledge & Implementation Context

> **Document purpose:** This document is the working product knowledge for the IDE/AI coding agent. It describes **what we are building, why we are building it, the intended architecture, the current assumptions, known risks, and the validation work that must happen before full implementation**.
>
> This is intentionally **not a rigid final technical specification**. Some architectural decisions must be confirmed through real AISStream observations during the source-profiling phase. The AI agent should not prematurely lock those decisions.

---

## 1. Product Overview

We are building an **end-to-end maritime real-time data platform** based on live AIS (Automatic Identification System) data.

The project is intended to demonstrate practical Data Engineering capabilities around:

- real-time/event-driven data ingestion
- WebSocket-based streaming
- Apache Kafka
- data validation and normalization
- durable data lake storage
- Parquet
- PostgreSQL + PostGIS
- real-time vessel state processing
- geospatial analytics
- historical vessel tracking
- port/anchorage intelligence
- backend APIs
- live map visualization
- operational reliability
- observability and failure recovery

The project should feel like a **small production-oriented maritime data platform**, rather than a simple dashboard consuming an API directly.

### High-level goal

Build a platform that can:

1. receive live AIS events from AISStream;
2. reliably ingest and distribute those events through Kafka;
3. persist raw historical data into S3 as Parquet;
4. maintain a near-real-time vessel state in PostgreSQL/PostGIS;
5. derive useful maritime intelligence from vessel movement;
6. expose current and historical data through an API;
7. visualize vessel traffic and movement on a map.

---

# 2. Why This Project Exists

The main objective is to demonstrate that we can design a system where **streaming data is treated as an event stream**, rather than simply polling an API and inserting rows into a database.

The architecture should therefore demonstrate genuine use cases for Kafka.

AISStream is particularly suitable because it provides AIS data through a persistent WebSocket connection.

Conceptually:

```text
AISStream WebSocket
        │
        ▼
Python Ingestion Service
        │
        ▼
      Kafka
     /     \
    /       \
   ▼         ▼
Raw Sink   Stream Processor
   │         │
   ▼         ▼
S3/Parquet  PostgreSQL/PostGIS
   │         │
   ▼         ▼
Historical   Current State
Analytics       │
                ▼
             Backend API
                │
                ▼
             Live Map
```

Kafka is not being added simply because "Kafka is a popular Data Engineering technology".

It exists because the source is a continuous stream and multiple downstream systems need to consume the same event stream independently.

For example:

- one consumer persists raw events;
- another maintains current vessel state;
- another could perform alerting;
- another could perform analytics.

# 3. Current Source: AISStream

The current source is **AISStream**, accessed through its WebSocket API.

The tested source is already working locally: the ingestion prototype has successfully connected and received AIS messages.

The connection is conceptually:

```text
Python
  │
  │ WebSocket
  ▼
wss://stream.aisstream.io/v0/stream
  │
  ▼
AIS events
```

AISStream is an event source, not our database.

Important characteristics already observed/documented:

- persistent WebSocket connection;
- API key required;
- API key must remain server-side;
- geographic bounding boxes are required;
- message-type filters are available;
- MMSI filters are available;
- multiple connections are supported within service limits;
- the consumer must continuously consume messages;
- the service can disconnect;
- reconnect logic is therefore required;
- AISStream does not provide durable historical replay in the same way a database/data lake does;
- therefore, our platform must persist events as soon as practical.

### Important architectural principle

AISStream is the **source of truth for live ingestion at the moment an event is received**, but it is **not our historical storage layer**.

Our platform must create its own durable history.

---

# 4. Important Distinction: AIS Events vs Application Logs

Do not call every AIS message a "log".

They are different things.

### AIS event

An AIS event is domain data received from the source.

Example:

```text
MessageType = PositionReport
MMSI = 368207620
Latitude = ...
Longitude = ...
Sog = ...
Cog = ...
Timestamp = ...
```

### Application log

A log is generated by our own ingestion/application infrastructure.

Examples:

```text
INFO WebSocket connected
INFO Subscription accepted
INFO AIS event received
INFO Kafka message published
WARN WebSocket disconnected
INFO Reconnecting in 2.4 seconds
ERROR Kafka publish failed
```

The system must maintain this distinction throughout implementation.

# 5. Product Scope

## 5.1 MVP

The MVP should focus on **reliable live vessel tracking and historical persistence**.

Minimum capabilities:

### Live ingestion

- connect to AISStream;
- subscribe to a defined geographic bounding box;
- receive AIS messages;
- decode WebSocket frames;
- validate incoming data;
- publish events to Kafka;
- handle disconnections;
- reconnect automatically;
- emit operational logs.

### Streaming backbone

Kafka should:

- receive AIS events;
- retain them for a configurable period;
- allow multiple independent consumer groups;
- allow downstream consumers to replay recent events;
- preserve ordering for events sharing the same partition.

### Historical storage

A raw consumer should:

- consume AIS events from Kafka;
- buffer events;
- write batches to S3;
- store data as Parquet;
- partition files appropriately by event date/time;
- avoid creating one tiny Parquet file per event.

### Current state

A stream processor should:

- consume relevant AIS events;
- maintain the latest known state of vessels;
- write/update PostgreSQL/PostGIS;
- track last-seen timestamps;
- expose current vessel locations.

### API / visualization

The backend should eventually expose:

- current vessels;
- vessel details;
- historical tracks;
- geographic filtering;
- basic maritime statistics.

The frontend should eventually provide:

- live vessel map;
- vessel markers;
- vessel information;
- historical route visualization.

## 7.1 Source Layer

```text

```

Responsibilities:

- provide message types;

# 8. Ingestion Service

The ingestion service will initially be implemented in Python.

Responsibilities:

1. establish WebSocket connection;
2. send subscription;
3. receive WebSocket frames;
4. decode UTF-8 JSON;
5. validate message structure;
6. perform minimal normalization;
7. add ingestion metadata;
8. publish events to Kafka;
9. emit operational logs;
10. reconnect after failure.

### Desired lifecycle

```text
DISCONNECTED
     │
     ▼
 CONNECTING
     │
     ▼
 SUBSCRIBING
     │
     ▼
 CONNECTED / CONSUMING
     │
     ├── event received
     │      │
     │      ▼
     │   decode
     │      │
     │      ▼
     │   validate
     │      │
     │      ▼
     │   publish Kafka
     │
     └── connection error
            │
            ▼
      exponential backoff
            │
            ▼
         reconnect
            │
            ▼
        re-subscribe
```

# 9. Reconnection Strategy

The connection must not assume that a WebSocket remains alive forever.

Use exponential backoff with jitter.

Example conceptual sequence:

```text
1s
2s
4s
8s
16s
...
```

with a maximum delay and random jitter.

Example:

```text
delay = min(base * 2^retry_count, max_delay) + jitter
```

The exact values can be decided during implementation.

### Why jitter?

If multiple instances reconnect simultaneously, jitter prevents synchronized reconnect storms.

### Important

The subscription configuration must be retained by the ingestion service so that after reconnecting it can automatically resubscribe.

# 10. Validation Strategy

Validation should occur in layers.

## 10.1 Transport/schema validation

Check:

- valid WebSocket frame;
- valid UTF-8;
- valid JSON;
- expected top-level structure;
- known/handled MessageType;
- required fields exist.

## 10.2 Domain/data validation

Examples:

```text
latitude ∈ [-90, 90]
longitude ∈ [-180, 180]
SOG >= 0
COG within valid domain
MMSI has valid structure
timestamp is parseable
```

The exact rules must be adapted after source profiling.

### Invalid records

Invalid events must not crash the ingestion service.

Possible flow:

```text
AISStream
    │
    ▼
Validation
   / \
  /   \
valid  invalid
 │       │
 ▼       ▼
Kafka   ais.invalid
```

A dead-letter/quarantine topic can be introduced if profiling confirms that it is useful.

# 11. Raw vs Normalized Data

This distinction is important.

The system should preserve enough source information to make historical debugging and replay possible.

A possible approach is:

```text
AISStream
   │
   ▼
Minimal validation
   │
   ▼
Kafka raw event
   │
   ├──────────────► Raw S3/Parquet
   │
   ▼
Normalization / processing
   │
   ▼
PostGIS / derived streams
```

Do not aggressively transform the source event before preserving it.

The final decision on whether Kafka should contain:

- source-like raw JSON;
- canonical normalized events;
- both;

must be made after source profiling.

# 15. Kafka Partitioning

The likely partition key is:

```text
MMSI
```

Reason:

Events belonging to the same vessel should ideally remain ordered within the same Kafka partition.

Kafka ordering is guaranteed **within a partition**, not globally across the topic.

However, the partition strategy must be confirmed after source profiling.

Do not assume the final number of partitions before measuring actual event volume.

---

# 16. Kafka Retention

Kafka is not intended to be the permanent historical warehouse.

Use Kafka for:

- buffering;
- decoupling;
- replay;
- recovery;
- independent consumers.

Use S3 for:

- durable history;
- long-term storage;
- analytical processing.

Conceptually:

```text
              Short/Medium Term
                    Kafka
                      │
                      ▼
                Replay window
                      │
                      ▼
Long-term history ──► S3
```

# 17. Raw Data Lake

The raw data lake will use:

```text
AWS S3
```

with:

```text
Parquet
```

### Important distinction

S3 is the storage system.

Parquet is the file format.

Parquet is useful because it provides:

- columnar storage;
- compression;
- efficient analytical reads;
- column pruning;
- better storage efficiency than naïve JSON/CSV storage for analytical workloads.

```text
            hour=HH/
```

The exact partitioning should be determined after measuring:

# 19. Parquet Write Strategy

The stream is continuous, so the raw sink must buffer events.

Conceptually:

```text
Kafka
  │
  ▼
Raw Consumer
  │
  ▼
Buffer
  │
  ├── enough records
  │
  └── flush interval reached
          │
          ▼
       Parquet
          │
          ▼
          S3
```

The system should use:

- size-based flush;
- time-based flush;
- retries;
- safe file naming;
- appropriate compression.

Exact batch size and flush interval will be selected after source profiling.

The primary concern is avoiding the **small-file problem**.

# 21. Vessel Status

The system may eventually derive operational states such as:

```text
UNDERWAY
ANCHORED
MOORED
STOPPED
STALE
UNKNOWN
```

Do not infer status from missing messages alone.

AIS is event-driven and message frequency can vary.

A better approach is to combine:

- NavigationalStatus;
- SOG;
- movement history;
- geofence;
- last_seen_at.

A vessel can be marked `STALE` when the last event exceeds an agreed threshold.

The threshold must be configurable and validated against actual source behavior.

---

# 22. Historical Vessel Tracking

Historical routes should not depend on the current-state table.

The current-state table only represents the latest known position.

Historical tracking should use persisted events:

```text
S3/Parquet
      │
      ▼
filter MMSI + time range
      │
      ▼
sort by event_time
      │
      ▼
route
```

This allows:

- route replay;
- historical track visualization;
- vessel movement analysis;
- traffic density analysis.

---

# 23. Port Intelligence

Port information is not necessarily a direct equivalent of a PositionReport.

A PositionReport tells us where a vessel is.

Port intelligence can be derived by combining vessel positions with geographic boundaries.

Conceptual approach:

```text
Position Event
      │
      ▼
Point-in-polygon
      │
      ▼
Port / Anchorage Geofence
      │
      ▼
State transition
```

Example:

```text
outside → inside
        = arrival candidate

inside → outside
        = departure candidate
```

Duration can then be derived from:

```text
departure_time - arrival_time
```

However, GPS/AIS noise can produce false transitions.

Therefore, port detection should eventually use:

- geofences;
- grace periods;
- hysteresis;
- minimum dwell time;
- movement state.

This should be implemented only after the basic live tracking pipeline works.

# 24. Data Quality Challenges

The system should assume that maritime data is imperfect.

Potential issues:

### Missing events

A missing AIS message does not necessarily mean that a vessel stopped transmitting.

### Duplicate events

The same event may potentially be observed or delivered more than once.

The system should investigate actual duplicate behavior before selecting a deduplication key.

### Out-of-order events

Network and processing delays can result in event-time ordering differing from ingestion-time ordering.

Therefore maintain both:

```text
event_time
ingested_at
```

### Invalid coordinates

Validate geographic ranges.

### Stale vessels

Use `last_seen_at`.

### Schema variation

Different MessageTypes have different structures.

Do not force all AIS messages into one flat schema.

# 42. Failure Scenarios and Mitigation

## 42.1 AISStream disconnect

### Risk

Live ingestion stops.

### Mitigation

- automatic reconnect;
- exponential backoff;
- jitter;
- resubscribe automatically;
- log connection state;
- monitor last received event.

---

## 42.2 AISStream service issue

### Risk

No events are available.

### Mitigation

- source-health monitoring;
- detect abnormal zero-event periods;
- preserve existing historical data;
- maintain a replay/sample dataset for development/testing;
- do not assume the source provides durable replay.

---

## 42.3 Slow consumer

### Risk

Kafka consumer falls behind.

### Mitigation

- monitor consumer lag;
- limit geographic scope initially;
- use message-type filtering;
- optimize serialization;
- batch downstream writes;
- scale consumers when necessary.

---

## 42.4 Invalid AIS data

### Risk

Malformed/unexpected data crashes processing.

### Mitigation

- schema validation;
- domain validation;
- quarantine/DLQ;
- structured error logs;
- continue processing valid events.

---

## 42.5 Duplicate events

### Risk

Historical data or current state becomes incorrect.

### Mitigation

- profile duplicates first;
- define event identity carefully;
- implement idempotent current-state updates;
- use deduplication where justified.

---

## 42.6 Kafka failure

### Risk

Events cannot be published or consumed.

### Mitigation

- producer retries;
- appropriate acknowledgements;
- persistent Kafka storage;
- consumer offsets;
- replay from Kafka;
- monitor producer/consumer errors.

---

## 42.7 S3 write failure

### Risk

Historical data is not persisted.

### Mitigation

- buffer before write;
- retry;
- do not acknowledge/commit Kafka offsets too early;
- ensure output naming is safe/idempotent;
- replay from Kafka after recovery.

The exact offset-commit strategy must be implemented carefully.

---

## 42.8 PostGIS failure

### Risk

Current-state map becomes stale.

### Mitigation

Kafka retains events.

After recovery:

```text
Kafka
  │
  ▼
reprocess events
  │
  ▼
rebuild current state
```

This is one of the key architectural benefits of Kafka.

---

## 42.9 API key exposure

### Risk

Credentials are leaked.

### Mitigation

- keep API key server-side;
- environment variables/secrets;
- never expose it to frontend;
- never commit secrets to Git;
- never place it in client-side code.

---

## 42.10 Schema change

### Risk

AISStream changes or adds fields/message types.

### Mitigation

- tolerate unknown fields where possible;
- version internal canonical schemas;
- profile source periodically;
- later introduce Schema Registry if complexity justifies it.

Do not introduce Schema Registry prematurely.

---

## 42.11 Port geofence false transitions

### Risk

AIS/GPS noise causes false arrival/departure events.

### Mitigation

- geofence;
- minimum dwell time;
- grace period;
- hysteresis;
- state machine;
- require multiple observations where appropriate.

---

## 42.12 Historical gaps

### Risk

A vessel appears to disappear.

### Mitigation

Do not interpret missing data automatically as inactivity.

Track:

```text
last_seen_at
```

and expose a state such as:

```text
STALE
UNKNOWN
```

# 45. Role of Airflow

Airflow is **not required for the live streaming path**.

Do not use:

```text
Airflow → poll AISStream every minute
```

as the core architecture.

The live stream is handled by:

```text
AISStream → WebSocket → Python → Kafka
```

Airflow may later be used for scheduled batch workflows such as:

- historical aggregation;
- data quality reports;
- warehouse/mart transformations;
- daily traffic analytics;
- partition maintenance;
- data lifecycle jobs.

Therefore:

```text
Kafka = streaming/event backbone
Airflow = scheduled batch orchestration
```

They solve different problems.

```text
measure first
→ decide second
→ implement third
```

## Rule 3 — Preserve raw data

Do not discard source fields unnecessarily.

Historical data should remain useful for debugging and future analytics.

---

## Rule 4 — Separate event time and ingestion time

Always distinguish:

```text
event_time
ingested_at
```

---

## Rule 5 — Treat failures as normal

The system must expect:

- disconnects;
- retries;
- invalid data;
- slow consumers;
- downstream failures.

Failure recovery is part of the architecture, not an afterthought.

---

## Rule 6 — Do not crash because of one bad event

A malformed event should be isolated.

---

```text

AISSTREAM_BOUNDING_BOX
KAFKA_BOOTSTRAP_SERVERS
KAFKA_TOPIC
S3_BUCKET
POSTGRES_URL
```

Do not hard-code secrets or environment-specific infrastructure.

The following should be testable independently:

- AISStream client;

- normalization;
- Kafka producer;
- S3 sink;
- PostGIS updater;
- API;
- geospatial logic.

---

## Rule 9 — Preserve replayability

Kafka offsets and durable storage should allow downstream components to recover from failures.
